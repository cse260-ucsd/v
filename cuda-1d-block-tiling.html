1D block tiling

1D block tiling gives each thread 2 numbers in a column of C instead of one. Both need the same number of Bs at every step, so the thread reads it from shared memory once, into a register, and uses it twice.

Follow
kernel matmul_1d(A, B, C, N): shared As[4][4], Bs[4][4] tx, ty = threadIdx.x, threadIdx.y r = blockIdx.y · 4 col = blockIdx.x · 4 + tx acc[0..1] = 0 for t in 0 .. N/4 − 1: for m in 0 .. 1: i = 2ty + m As[i][tx] = A[r + i][4t + tx] Bs[i][tx] = B[4t + i][col] sync() for k in 0 .. 3: b = Bs[k][tx] acc[0] += As[2ty][k] · b acc[1] += As[2ty + 1][k] · b sync() C[r + 2ty][col] = acc[0] C[r + 2ty + 1][col] = acc[1]

In a real implementation

  1. Strip length. The number of sums per thread is a parameter to tune. With TM numbers of a column of C per thread, each number read from Bs feeds TM multiply-adds: TM + 1 reads of shared memory for TM multiply-adds, against 2 · TM in Part 2. Longer strips need more registers (below), so time a few lengths on the Tesla T4 to find the fastest.
  2. Registers. Every sum takes a register, and the threads on an SM (streaming multiprocessor) share its registers. A Tesla T4 SM has 65,536: 64 per thread when all 1,024 threads it can hold are there. Threads that need more fit fewer per SM, which leaves fewer warps to switch to while one waits for memory. Independent multiply-adds within each thread make up for some of that: the two here don't wait for each other.
  3. Arrays in registers. acc[0..1] stays in registers only because every index into it is a constant. When the compiler can't tell that, the array goes to local memory, which sits in global memory and is just as slow. Real kernels loop over the strip with #pragma unroll, which turns every index into a constant.
