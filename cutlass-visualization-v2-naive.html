Naive

The simplest kernel gives every number of C its own thread, which reads a row of A and a column of B straight from global memory. Memory serves the threads of a warp together, so their loads are coalesced only if the warp reads neighbors.

In a real implementation

The picture shrinks an NVIDIA Tesla T4 to fit on screen. The kernel runs on it as written; what changes is scale, and how the hardware schedules the work.

  1. Warps. A warp has 32 threads, not 4. It takes 32 consecutive thread IDs, counted along threadIdx.x first, so in a block 16 threads wide, each warp covers two rows of threads.
  2. Sizes. A block can have up to 1,024 threads. The best size depends on the kernel, the GPU and the matrices: time a few to find it. Matrices worth a GPU are hundreds to thousands of numbers per side, so the grid has far more than 4 blocks.
  3. Running at once. In the picture, every thread takes each step together. A T4 has 40 streaming multiprocessors (SMs), each holding at most 16 blocks and 1,024 threads at a time; further blocks wait for a free SM. Each SM has 4 warp schedulers. Each one issues an instruction for one warp at a time, and switches to another warp while one waits for memory.
  4. Memory chunks. A chunk is 32 bytes: 8 floats, not 4. A warp reading 32 neighbors along a row needs 4 chunks, 128 bytes. Reading down a column, it needs 32 chunks and uses 4 bytes of each.
  5. Caches. The picture fetches every chunk from memory. A T4 keeps recent chunks in its L1 and L2 caches, so with threadIdx.x → row, the chunk fetched for A[r][0] may still hold A[r][1] to A[r][7] at the next steps. Each chunk is still a separate 32-byte access, cached or not, so reading down a column still takes 32 accesses where reading along a row takes 4.
  6. Sizes that don't divide. This launch makes N / 4 blocks per side, which covers C only when N is a multiple of 4. Real code rounds the grid up and has threads outside the matrix skip the work: if (row < N && col < N).
