1The problem: cheap math, expensive data

A GEMM computes D = α·A·B + β·C, where A is M×K, B is K×N and C and D are M×N. Each output element is the dot product of a row of A and a column of B: K multiplies and K adds. The whole problem is 2·M·N·K floating-point operations on only M·K + K·N + M·N numbers.

That ratio is what the rest of this page is about. A naive kernel gives each thread one output and reads its row and column straight from global memory. It moves 4 bytes (two FP16 values) for every 2 FLOPs. A modern GPU needs roughly 150–300 FLOPs per byte of DRAM traffic to keep its Tensor Cores busy. CUTLASS closes that gap by reusing every loaded value many times out of smaller, faster memories.

2The tiling hierarchy

CUTLASS applies one idea recursively: split C into tiles, and for each tile march along K, accumulating products of an A sliver and a B sliver. Each level of the split sits at a different level of the memory hierarchy:

  1. Grid → threadblock (CTA) tiles. Each CTA owns a BM×BN tile of C. Its A and B slivers stream from global memory, through L2, into shared memory one BK-wide k-tile at a time.
  2. CTA → warp tiles. The CTA's warps split its tile between them. Each warp copies its rows of the A tile and its columns of the B tile from shared memory into registers.
  3. Warp → MMA instructions. A warp tile is a grid of Tensor Core instructions (16×8×16 for SM80 mma.sync), and all 32 lanes execute each one together.
  4. Instruction → thread. Inside one MMA, each lane holds a few elements of A, B and C in its registers, in a fixed fragment layout (§7).

The accumulators for the CTA's whole tile stay in registers, spread across its threads, for the entire K loop. C is touched once, at the very end.

3Why tiles: reuse, and what it costs

For each k-step, a BM×BN CTA tile loads (BM + BN)·BK elements and performs 2·BM·BN·BK FLOPs with them. Every A element is reused BN times and every B element BM times. Its arithmetic intensity with respect to global memory is

intensity = 2·BM·BN / ((BM + BN) · bytes per element) FLOP/byte

It grows with the tile and doesn't depend on BK. So why not use huge tiles? Three costs grow with them. Accumulators live in registers: BM·BN·4 bytes per CTA, out of a 256 KB register file per SM. Every pipeline stage needs (BM + BN)·BK·bytes of shared memory. And bigger tiles leave fewer CTAs to spread across the SMs (§8). Picking a tile shape means balancing all three.

4The mainloop, one k-tile at a time

Here is a single 128×128 CTA with four 64×64 warps working through K = 256 in k-tiles of 32. Each iteration of its mainloop does four things:

  1. Copy. An asynchronous copy brings the next A and B k-tiles from global memory into a free shared-memory buffer. On Ampere this is cp.async; on Hopper it is one TMA instruction. The data never passes through registers.
  2. Wait. Before computing on a buffer, threads wait for its copy to land and then synchronize: cp.async.wait_group + __syncthreads(), or an mbarrier on Hopper.
  3. Compute. Each warp loads fragments with ldmatrix and issues (64/16)·(64/8)·(32/16) = 64 mma.sync instructions, accumulating into registers.
  4. Release. Once every warp is done with a buffer, it is refilled with a later k-tile.

5Software pipelining: hide latency, respect bandwidth

A global-memory load takes hundreds of cycles to come back. With one buffer, a CTA alternates between waiting and computing. With S stages, up to S k-tiles are in flight while the Tensor Cores work on one that has already landed. In steady state each k-tile takes about

period ≈ max( compute, transfer, (compute + latency) / S )

so latency is hidden once S ≥ 1 + latency / compute. Bandwidth is a different limit. If moving a k-tile takes longer than computing on it, adding stages does nothing; only more reuse helps (bigger tiles, better L2 hit rates). CUTLASS exposes the stage count as a template parameter. CUTLASS 3.x can also choose it automatically from the shared memory left over after the epilogue's needs (StageCountAutoCarveout).

6Shared memory: banks, conflicts and swizzling

Shared memory is divided into 32 banks, each 4 bytes wide, with consecutive 4-byte words in consecutive banks. A request completes in one pass (a "wavefront") per 128 bytes only if its threads touch distinct banks, or the same word. When threads hit different addresses in the same bank, the accesses serialize.

ldmatrix reads each 8×8 FP16 matrix as eight 16-byte rows, which in a K-major tile is a column of 16-byte chunks. If each tile row is 128 bytes (64 FP16 values), every row starts at bank 0. All eight chunks then land in the same four banks: an 8-way conflict. There are two common fixes:

  • Padding each row by 16 bytes shifts each row four banks over from the one above. It works, but it wastes space and breaks the dense layout that TMA and wide copies want.
  • XOR swizzling permutes the 16-byte chunks within each row: chunk′ = chunk ⊕ (row mod 8). Rows stay contiguous, so row-wise copies stay conflict-free, and any column of chunks spreads across all 32 banks. In CuTe this is Swizzle<3,3,3> applied to the element offset.

7Inside one Tensor Core instruction

mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32 multiplies a 16×16 A fragment by a 16×8 B fragment and adds the product to a 16×8 accumulator: 4096 FLOPs from one warp-wide instruction. No thread owns a whole matrix. The operands are spread across the 32 lanes' registers. Lane ℓ belongs to group g = ℓ ÷ 4, which decides its rows, and has index t = ℓ mod 4 within the group, which decides its pair of columns.

Each lane holds four 32-bit registers of A (8 halves), two of B (4 halves) and four FP32 accumulators. ldmatrix.x4 builds the A fragment from shared memory in exactly this layout. Lane ℓ supplies the address of row ℓ mod 16, column (ℓ ÷ 16)·8, and the hardware routes the data so every lane receives its fragment.

Fragment layout of mma.sync m16n8k16
Hover a lane, or any cell, to see the registers that lane holds. Colors identify the group g (one color per four lanes).

Hopper's wgmma.mma_async runs on a warpgroup (4 warps, 128 threads) with shapes m64nNk16, where N can be up to 256. It reads B, and optionally A, directly from shared memory through descriptors, and it runs asynchronously. Blackwell's tcgen05.mma goes further: a single thread issues it, and the accumulator lives in dedicated Tensor Memory rather than in registers.

8Scheduling CTAs: rasterization, waves, split-K, stream-K

A GPU runs only as many CTAs at once as fit on its SMs. That set is called a wave, and it has two consequences.

L2 locality

CTAs in the same wave that share an A row-panel or a B column-panel can hit in L2 instead of going to DRAM. Launching tiles in row-major order sweeps a whole row of C, so a wave touches nearly every B panel. A swizzled (grouped) order keeps each wave inside a compact block of tiles, so far fewer distinct panels are live at once. In CUTLASS 2.x this is the ThreadblockSwizzle template parameter; in 3.x it belongs to the tile scheduler.

Rasterization and L2 footprint
Numbers show launch order. The A and B panels used by the highlighted wave are shaded. Fewer distinct panels per wave means more reuse from L2.

Wave quantization

Tiles come in whole units. With 132 SMs and 144 tiles, the second wave runs 12 tiles while 120 SMs sit idle. Split-K cuts each tile's K loop into s pieces, giving more and shorter work units, at the cost of a reduction over partial sums. Stream-K divides the total number of mainloop iterations evenly across a persistent set of CTAs, one per SM. When a tile's K range is split between two CTAs, a small "fixup" step adds their partial accumulators together.

Work distribution over time
Each row is an SM, time runs to the right, and colors identify output tiles. CUTLASS's stream-K scheduler can also run a hybrid: whole waves data-parallel, with stream-K only for the leftover tiles.

9The epilogue

When the mainloop finishes, the CTA's tile of results sits in registers in MMA fragment layout. The epilogue applies the output operator and writes D. The classic operator is D = α·acc + β·C, often fused with a bias, an activation (ReLU, GELU), scaling or a type conversion. Fusing these here saves a full extra round trip of D through memory.

Why the detour through shared memory? In the fragment layout, each thread holds two adjacent values per row, four threads share a row, and one instruction spans eight rows. Storing straight from registers therefore produces narrow, scattered writes. Rearranging the tile through shared memory lets every thread write 16 contiguous bytes and every warp cover whole 128-byte lines.

10CuTe: layouts are functions

CUTLASS 3.x is built on CuTe. A tensor is a pointer plus a Layout, and a layout is a function from logical coordinates to memory offsets, written Shape:Stride. For example, (4,8):(1,4) is a 4×8 column-major matrix and (4,8):(8,1) is row-major. Modes can nest: in ((2,2),(2,4)):((1,4),(2,8)) both modes are themselves split in two, so the matrix is stored as contiguous 2×2 blocks. A coordinate's offset is the inner product of its hierarchical coordinate with the strides.

Everything in the earlier sections can be written as CuTe layouts and operations on them (composition, logical_divide, local_tile, local_partition): CTA tiles, warp partitions, the per-lane fragments of §7 and the swizzle of §6. That is why the tiling code looks the same at every level.

11Putting it together

The template parameters of a CUTLASS GEMM map directly onto the ideas above. Below are a CUTLASS 2.x kernel for SM80 and its CUTLASS 3.x equivalent for SM90, both shortened to their essentials.

CUTLASS 2.x · SM80 · mma.sync
using Gemm = cutlass::gemm::device::Gemm<
  cutlass::half_t, cutlass::layout::RowMajor,     // A
  cutlass::half_t, cutlass::layout::ColumnMajor,  // B
  float,           cutlass::layout::RowMajor,     // C, D
  float,                                          // accumulator
  cutlass::arch::OpClassTensorOp,
  cutlass::arch::Sm80,
  cutlass::gemm::GemmShape<128, 128, 32>,  // CTA tile (§2-3)
  cutlass::gemm::GemmShape<64, 64, 32>,    // warp tile (§2)
  cutlass::gemm::GemmShape<16, 8, 16>,     // mma.sync shape (§7)
  cutlass::epilogue::thread::LinearCombination<
      float, 4, float, float>,             // alpha*acc + beta*C (§9)
  cutlass::gemm::threadblock::GemmIdentityThreadblockSwizzle<>, // (§8)
  3>;                                      // stages (§4-5)

Gemm gemm_op;
gemm_op({{M, N, K}, {A, lda}, {B, ldb}, {C, ldc}, {D, ldd}, {alpha, beta}});
CUTLASS 3.x · SM90 · TMA + wgmma
using TileShape    = Shape<_128, _128, _64>;  // CTA tile (§2-3)
using ClusterShape = Shape<_1, _2, _1>;       // CTAs sharing TMA multicast
// using Epilogue = epilogue::collective::CollectiveBuilder<...>::CollectiveOp; (§9)

using Mainloop = typename cutlass::gemm::collective::CollectiveBuilder<
    cutlass::arch::Sm90, cutlass::arch::OpClassTensorOp,
    cutlass::half_t, cutlass::layout::RowMajor, 8,     // A, alignment
    cutlass::half_t, cutlass::layout::ColumnMajor, 8,  // B, alignment
    float, TileShape, ClusterShape,
    cutlass::gemm::collective::StageCountAutoCarveout<
        sizeof(typename Epilogue::SharedStorage)>,     // stages (§5)
    cutlass::gemm::KernelTmaWarpSpecializedCooperative // schedule
  >::CollectiveOp;

using Kernel = cutlass::gemm::kernel::GemmUniversal<
    Shape<int, int, int, int>,       // M, N, K, batch
    Mainloop, Epilogue,
    cutlass::gemm::PersistentScheduler>; // or StreamKScheduler (§8)
using Gemm = cutlass::gemm::device::GemmUniversalAdapter<Kernel>;
